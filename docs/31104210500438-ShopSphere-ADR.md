# Architecture Decision Record — ShopSphere Modernization

**Status:** Accepted · **Date:** 2026-08-25

## 1. Microservice extraction: Reviews

**Decision:** Product reviews were moved out of the monolith into a
standalone `review-service` (own codebase, own Prisma schema/database
table, own deployment on Vercel, own URL). The main backend no longer
contains any review model, controller, or route — the frontend calls the
review service directly over REST (`GET/POST /api/reviews/:productId`,
`DELETE /api/reviews/:id`), using a shared `JWT_SECRET` so the review
service can trust the identity in a token issued by the main app without
owning a users table itself.

**Why reviews:** Of the monolith's four resources (products, cart, orders,
reviews), reviews are the most independent: they have no foreign-key
relationship that matters operationally (a review's `productId` is just an
opaque string reference, never joined against in a transaction), they're
written and read far more often than products/orders change, and they're
the one resource whose read load (browsing reviews) is decoupled from
write-consistency requirements (unlike orders, which must stay
transactionally consistent with stock). That makes reviews low-risk to run
as an eventually-consistent, independently-scaled service, and a clean
seam to cut the monolith along without touching checkout, cart, or auth.

## 2. Serverless workload: Product rating sync

**Decision:** A single Vercel Serverless Function,
`api/sync-product-ratings.ts`, runs on a daily Vercel Cron schedule. It
calls the review service's REST API for every product, computes nothing
locally (the review service already returns `averageRating`/`count`), and
writes the aggregate back into the main Postgres `products` table's
`rating` / `numReviews` columns.

**Why this workload:** The product list and product cards render `rating`
and `numReviews` on every page load, and doing that with a live REST call
to the review service per product, per page view, would make the review
service a hard dependency for basic browsing (Task 3.2 already requires
end-to-end resilience). Denormalizing the aggregate onto `products` keeps
browsing fast and independent of the review service's uptime, at the cost
of the numbers being *slightly* stale between syncs — an acceptable
trade-off for a rating average, and exactly the kind of periodic,
non-request-driven aggregation work serverless cron functions are for. It
also has a clear, bounded (not open-ended) execution window, which fits
Vercel's serverless execution model rather than needing a long-running
worker process.
